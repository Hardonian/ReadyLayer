# What ReadyLayer Is Not

## Purpose of This Document

This document explicitly defines what ReadyLayer is **not** designed to do, to prevent misaligned expectations, scope creep, and positioning confusion. These boundaries are intentional and will not change.

Understanding what ReadyLayer does not attempt to solve is as important as understanding what it does.

---

## ReadyLayer Is Not a Linter

### What Linters Do

Linters enforce code style, detect syntactic issues, and identify violations of predefined coding standards (formatting, naming conventions, deprecated API usage).

### Why ReadyLayer Is Different

ReadyLayer does not:
- Enforce code formatting or style preferences
- Flag unused imports or variables (unless they represent security risks)
- Require specific naming conventions
- Detect missing semicolons or whitespace issues

**Rationale**: Style enforcement is a solved problem with excellent existing tools (ESLint, Prettier, RuboCop, etc.). ReadyLayer focuses on **semantic correctness and governance**, not syntactic style.

**Use both**: Run your linter in CI. Run ReadyLayer for governance. They serve complementary purposes.

---

## ReadyLayer Is Not a Replacement for Tests

### What Testing Frameworks Do

Testing frameworks (Jest, pytest, RSpec, etc.) validate that code behaves as specified under controlled conditions. They provide regression detection and specification enforcement.

### Why ReadyLayer Is Different

ReadyLayer does not:
- Replace your unit tests
- Replace your integration tests
- Replace your E2E tests
- Provide test execution infrastructure

**Rationale**: Tests validate **behavior**. ReadyLayer validates **governance** (did this code go through proper review? does it meet policy requirements? is there an audit trail?).

ReadyLayer can:
- Analyze test coverage as an input to governance decisions
- Detect when AI-generated code lacks adequate tests
- Ensure tests were reviewed alongside code

But it does not execute or replace tests.

**Use both**: Write comprehensive tests. Use ReadyLayer to ensure governance policies are met before merge.

---

## ReadyLayer Is Not an AI Model

### What AI Models Do

AI models (GPT-4, Claude, Gemini, etc.) generate code, answer questions, and provide suggestions based on learned patterns.

### Why ReadyLayer Is Different

ReadyLayer does not:
- Generate code
- Provide coding suggestions or autocomplete
- Train on your codebase
- Improve code quality through generation

**Rationale**: ReadyLayer is **model-agnostic governance infrastructure**. It works with code generated by any AI model (or human-written code). It does not compete with or replace AI coding assistants.

ReadyLayer **does** use AI models internally for:
- Code review enrichment (detecting subtle issues)
- Documentation validation
- Test adequacy analysis

But these are **governance functions**, not generation functions.

**Use both**: Use AI assistants to write code. Use ReadyLayer to govern what gets merged.

---

## ReadyLayer Is Not an IDE

### What IDEs Do

Integrated Development Environments (VS Code, IntelliJ, Vim, etc.) provide code editing, debugging, navigation, and developer experience tooling.

### Why ReadyLayer Is Different

ReadyLayer does not:
- Provide a code editor
- Offer IDE plugins (currently)
- Replace your development environment
- Provide debugging tools

**Rationale**: Developers have strong preferences for their editing environment. ReadyLayer operates at the **repository and CI layer**, not the developer workstation layer.

Future integrations may provide IDE feedback (e.g., "this change will be blocked by policy"), but ReadyLayer will never be an IDE itself.

**Use both**: Write code in your preferred IDE. ReadyLayer validates at commit/PR time.

---

## ReadyLayer Is Not a Policy Engine Owned by Vendors

### What Vendor Policy Engines Do

Some platforms (GitHub, GitLab, Bitbucket) provide policy enforcement features tied to their ecosystems. These are valuable but vendor-locked.

### Why ReadyLayer Is Different

ReadyLayer does not:
- Lock you into a specific git provider
- Require using a specific CI system
- Force you onto a specific AI model provider
- Monetize through vendor lock-in

**Rationale**: Governance infrastructure must be **neutral** to be trusted. ReadyLayer is:
- Open source
- Self-hostable
- Provider-agnostic (works with GitHub, GitLab, Bitbucket, etc.)
- Model-agnostic (works with OpenAI, Anthropic, local models, etc.)

Vendor-provided policy engines are complementary, not competing. ReadyLayer provides **portable governance** that survives platform migrations.

**Use both**: Use platform-specific policies where appropriate. Use ReadyLayer for cross-platform, durable governance.

---

## ReadyLayer Is Not a Security Scanner

### What Security Scanners Do

Security scanners (Snyk, Dependabot, CodeQL, etc.) detect known vulnerabilities, dependency issues, and security-specific antipatterns (SQL injection, XSS, etc.).

### Why ReadyLayer Is Different

ReadyLayer does not:
- Replace CVE scanning
- Replace dependency vulnerability detection
- Replace SAST/DAST tools
- Maintain a vulnerability database

**Rationale**: Security scanning is a specialized domain with excellent dedicated tools. ReadyLayer integrates with these tools rather than replacing them.

ReadyLayer **does**:
- Ensure security scan results are reviewed before merge
- Enforce policies based on security findings (e.g., "block if critical CVEs detected")
- Provide governance audit trails for security decisions

But it does not perform the scanning itself.

**Use both**: Run security scanners in your CI pipeline. Use ReadyLayer to enforce governance policies based on their findings.

---

## ReadyLayer Is Not a Compliance Framework

### What Compliance Frameworks Do

Compliance frameworks (SOC 2, ISO 27001, HIPAA, etc.) define **what** policies an organization must have to meet regulatory or certification requirements.

### Why ReadyLayer Is Different

ReadyLayer does not:
- Define compliance requirements for your organization
- Provide legal or regulatory advice
- Certify your compliance status
- Replace compliance audits

**Rationale**: Compliance requirements vary by industry, geography, and organization. ReadyLayer provides the **infrastructure** to implement and audit compliance policies, but does not define them.

ReadyLayer **does**:
- Provide immutable audit trails (required for many compliance frameworks)
- Allow policy definition that maps to compliance requirements
- Generate compliance reports based on governance activity
- Ensure deterministic, auditable decision-making

**Use both**: Define compliance policies with your legal/compliance team. Use ReadyLayer to enforce and audit them.

---

## ReadyLayer Is Not a Code Quality Metric Dashboard

### What Code Quality Dashboards Do

Tools like SonarQube, Code Climate, and Codacy provide metrics dashboards showing code quality trends, technical debt, and maintainability scores.

### Why ReadyLayer Is Different

ReadyLayer does not:
- Calculate code complexity metrics (cyclomatic complexity, cognitive complexity)
- Provide "code health" scores
- Offer vanity metrics or gamification
- Generate charts for management reporting

**Rationale**: Code quality metrics are useful but often become targets that distort behavior (Goodhart's Law). ReadyLayer focuses on **governance enforcement**, not metric optimization.

ReadyLayer **does**:
- Provide audit trails showing what was reviewed, by whom, and when
- Show policy compliance rates
- Report governance anomalies (e.g., unexpected policy bypass)

These are **governance metrics**, not code quality metrics.

**Use both**: Use quality dashboards for team improvement. Use ReadyLayer for governance enforcement.

---

## ReadyLayer Is Not a CI/CD Platform

### What CI/CD Platforms Do

CI/CD platforms (GitHub Actions, GitLab CI, Jenkins, CircleCI, etc.) execute build pipelines, run tests, and deploy code.

### Why ReadyLayer Is Different

ReadyLayer does not:
- Execute build scripts
- Deploy applications
- Manage infrastructure
- Orchestrate test runs

**Rationale**: CI/CD is infrastructure. ReadyLayer is a governance layer that integrates with CI/CD platforms but does not replace them.

ReadyLayer **does**:
- Integrate with CI/CD via webhooks and API calls
- Block merges based on governance policies (enforced in CI)
- Provide governance status checks (pass/fail gates)

**Use both**: Use your existing CI/CD platform. Add ReadyLayer as a governance gate.

---

## ReadyLayer Is Not a Documentation Tool

### What Documentation Tools Do

Documentation tools (Docusaurus, Sphinx, JSDoc, etc.) generate and host documentation from code comments and markdown files.

### Why ReadyLayer Is Different

ReadyLayer does not:
- Generate documentation websites
- Render markdown or API docs
- Host documentation
- Provide documentation templates

**Rationale**: Documentation generation is a content problem. ReadyLayer addresses a **validation** problem.

ReadyLayer **does**:
- Validate that documentation exists and is up-to-date
- Detect documentation drift (code changed but docs didn't)
- Ensure AI-generated code includes adequate documentation
- Enforce documentation policies before merge

**Use both**: Use documentation generators for creating docs. Use ReadyLayer to ensure they stay current.

---

## ReadyLayer Is Not a Training Platform

### What Training Platforms Do

Developer training platforms (Pluralsight, Udemy, internal training programs) teach developers new skills and best practices.

### Why ReadyLayer Is Different

ReadyLayer does not:
- Teach developers how to write better code
- Provide interactive coding tutorials
- Offer certification programs
- Replace code review as a learning tool

**Rationale**: Training is about skill development. ReadyLayer is about governance enforcement.

ReadyLayer **does**:
- Provide feedback on policy violations (which can be educational)
- Create audit trails that can inform training needs
- Surface patterns that indicate skill gaps

But education is a side effect, not a primary goal.

**Use both**: Invest in developer training. Use ReadyLayer to enforce consistent standards.

---

## ReadyLayer Is Not Attempting to Stop AI Code Generation

### What Some Organizations Do

Some organizations ban or heavily restrict AI code generation tools due to fear of IP leakage, quality concerns, or risk aversion.

### Why ReadyLayer Takes a Different Approach

ReadyLayer does not:
- Block developers from using AI assistants
- Require approval before using AI tools
- Monitor developer tool usage
- Advocate for banning AI generation

**Rationale**: AI code generation is inevitable and provides real productivity gains. Attempting to ban it:
- Reduces competitive velocity
- Encourages shadow IT (developers use tools anyway)
- Creates enforcement burdens
- Ignores the actual problem (lack of governance, not use of AI)

ReadyLayer **does**:
- Accept AI generation as a permanent fixture
- Provide governance for AI-generated code
- Ensure code quality regardless of authorship (human or AI)
- Create audit trails for generated code

**Philosophy**: The solution to AI code risk is not restriction—it's governance.

---

## ReadyLayer Is Not Feature-Complete

### Transparency About Scope

ReadyLayer is an evolving platform. It does not:
- Solve every governance problem
- Support every possible integration
- Provide every feature every organization needs

**Rationale**: Over-promising creates disappointment. We are transparent about what works now and what is planned.

Current limitations include:
- Limited IDE integrations (API available for community plugins)
- Primary focus on code review governance (expanding to other domains)
- Self-hosting requires technical expertise (managed offering in development)

**Commitment**: We will never claim ReadyLayer is a complete solution. It is foundational infrastructure that:
- Solves the core governance problem for AI-generated code
- Provides extension points for additional capabilities
- Integrates with specialized tools for specific needs

## Why These Boundaries Matter

Defining what ReadyLayer is **not** serves several purposes:

### Prevents Scope Creep

By clearly stating what we will not build, we protect focus on the core governance mission.

### Reduces Confusion

Users understand exactly what problem ReadyLayer solves and what complementary tools they still need.

### Avoids Competition with Allies

Many of these categories contain excellent existing tools. ReadyLayer integrates with them rather than competing.

### Builds Trust

Transparency about limitations builds trust. Over-promising and under-delivering destroys it.

### Enables Ecosystem Growth

By being a focused governance layer, ReadyLayer creates integration opportunities rather than vendor lock-in.

---

## Conclusion

ReadyLayer is purpose-built infrastructure for continuous governance of AI-generated code. It is:

- **Not** a replacement for existing development tools
- **Not** trying to solve every problem
- **Not** vendor-locked

It **is**:
- Focused on deterministic, auditable governance
- Complementary to existing tooling
- Neutral infrastructure that survives platform changes

If you are looking for a tool that replaces linters, tests, AI models, IDEs, security scanners, or CI/CD platforms, ReadyLayer is not that tool.

If you are looking for governance infrastructure that ensures AI-generated code meets your organization's policies, provides immutable audit trails, and operates at the velocity of AI generation—ReadyLayer is purpose-built for exactly that.

Use the right tool for each job. Use ReadyLayer for governance.
